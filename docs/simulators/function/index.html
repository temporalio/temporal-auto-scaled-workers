No-Sync Scaling Simulator

Scaling rules

Scale-up

  1. Task-add no-sync — if an arrival cannot dispatch immediately, one worker invoke is requested after scale-up cooloff has elapsed.
  2. Metrics poll (every metrics poll interval):
    1. Queue depth > backlog threshold and cooloff elapsed → invoke worker
    2. Otherwise, queue non-empty and max worker lifetime elapsed → invoke worker
    3. If dispatch rate is unchanged within epsilon → suppress the candidate
    4. Otherwise → no action

ε > 0 enables the flat dispatch rate detection (proposal): the poll's "dispatch flat despite a backlog" verdict is confirmed over a window, persisted, and read by the task-add path, which simply obeys the suppression lease — so growth is gated on both paths, while lifetime maintenance stays on the poll path; the poll backs off (re-checks less often) while suppressing. ε = 0 is exactly today's behavior. Cold start and the dispatch-rate window model real-world physics; the fast path fires per ~500 ms no-sync signal batch (fixed).

Scale-down

The no-sync algorithm does not scale down.

Simulator guard

Applied before a worker is added to keep the browser simulation bounded:

  • Worker count ≥ max workers → blocked
  • Worker age ≥ worker exit after → removed, active tasks requeued
